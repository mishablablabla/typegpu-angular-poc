## L1 — Deleting the last shader module leaves its output importable (stale shader bundled)
- **Severity** P2. **Status** FIXED. **Config** prebuild mode, Angular 22.2.4/npm, packed tarball d8d71d75; any project with exactly one shader module (the generated project has one).
- **Contract / invariant** README "Shader prebuild": a bare `ng build` cannot bundle a shader that is older than its source; QA_PLAN S13 "stale artifacts are never bundled".
- **Reproduction** (`<scratch>/qa/lead/sm.mjs s15`): project from `ng add --shaders prebuild` + `ng generate … my-canvas`; `ng build` ok; delete `src/app/my-canvas/my-canvas.gpu.ts` (the component still imports `@shaders/app/my-canvas/my-canvas.gpu`); `ng build -c development`.
- **Expected** build fails (unresolved `@shaders/...` import, or at least the stale module is gone). **Actual** exit 0; `shaders-dist/app/my-canvas/my-canvas.gpu.js` still present; the deleted shader's code is in `dist/`. The same in watch mode (`ng serve`): after deleting the only shader the output stays (observed in `sm.mjs s14`: "delete … its output is pruned" FAILED).
- **Root cause** `lib/tools/typegpu-shaders/build.mjs` (empty-closure early return `entries.length === 0 && allowEmpty`) and `ensure.mjs` (`entries.length === 0 → { ok: true, skipped: 'empty' }`) return before `prune`, before the manifest is touched and before the import scan. Works for ≥2 shaders (S13 passed), so it only shows with the last one.
- **Impact** a deleted/renamed last shader whose import was not updated keeps shipping the old shader silently; also hides the error Angular would otherwise report.
- **Fix** (worktree) `manifest.mjs` (`removeGenerated`, manifest now lists the files it generated), `build.mjs` and `ensure.mjs` call it for an empty closure; `ensure` then runs the import scan with `unresolved: true`, so a dangling `@shaders/…` import fails with the usual message. Behaviour tightened: a project with NO shader modules that still imports `@shaders/...` now fails in the tool instead of in Angular (premise of `delegate.spec` "a project without shader modules builds as before" corrected: its `main.ts` must not import `@shaders`).
- **Regression tests** `lib/schematics/testing/tools/typegpu-shaders/ownership.spec.ts` ("the last shader module is deleted…", 3 tests). Mutation check: removing the cleanup in `ensure.mjs` or in `build.mjs` fails them (killed); they failed on the pre-fix code path.
- **Uncertainty** none about the mechanism; the real-CLI re-run after the fix is logged separately.

## L2 — The tool deletes files it did not write, follows symlinks, and accepts an `out` that contains the project
- **Severity** P1 (data loss; destructive, silent). **Status** FIXED. **Config** `typegpu-shaders` CLI and wrapper builders, any (`typegpu-shaders.config.json` `out`, `--out`).
- **Contract** README: "writes `shaders-dist/`" (a dedicated generated folder, git-ignored). Nothing says other content of the chosen folder is deleted.
- **Reproduction A** (safe sandbox, `<scratch>/qa/lead/decoy/t.mjs`): `put generated/README-user.md`, `generated/sub/important.json`; `typegpu-shaders build --out generated` → both user files are gone after ONE build.
- **Reproduction B (incident)** a regression test I wrote ran `buildShaders({ root, out: '.' })` in a temp project whose `node_modules` is a symlink to `lib/node_modules`: the build emptied the project folder AND, following the symlink, **emptied the repository's `lib/node_modules`** (restored with `npm ci`, 228 packages; dependent runs of other lanes between 21:22 and 21:23 are invalid and were re-run). This is what any user with `out: '.'`, a pnpm/npm symlink farm or a monorepo could hit.
- **Expected** never delete what the tool did not write; refuse an `out` that is or contains the sources/project. **Actual** `prune()` (manifest.mjs) walked `out` recursively with `statSync` (follows symlinks) and removed every file not in the current output set.
- **Root cause** `lib/tools/typegpu-shaders/manifest.mjs` `prune` (walk-and-delete) + `config.mjs` validated only `src !== out`.
- **Impact** loss of user files (or an entire project/dependency tree) on a misconfiguration; recovery needs backups. Also, `ng add` never sets such an `out`, so the default path is safe: likelihood low, severity high.
- **Fix** (worktree) manifest records `generated` (every file the tool may write, claimed BEFORE the first write so a killed build leaves the list); `prune` removes only listed files that are no longer outputs and then only empty parent folders; nothing is walked, nothing followed; `config.mjs` rejects an `out` equal to, containing, or above the project root or `src`. Manifest `schema` 3 (older manifests are treated as unknown: one rebuild, no deletion).
- **Regression tests** `ownership.spec.ts` ("only what the tool wrote is ever deleted", 6 tests incl. `.`, `..`, `src`, `src/..`; the tests resolve the configuration only, never build with a dangerous `out`). Mutation check: walk-and-delete prune and no-validation mutants are killed.
- **Uncertainty** Windows junction handling not tested.

### C3 — green freshness for output built from different sources (A→B→A)
P1 by impact, low likelihood. `build.mjs` hashed the sources first and read them again later (esbuild/Babel, TypeScript); if the sources changed to B and back to A inside that window, the manifest paired hash(A) with output built from B (digest taken from the written bytes). After the revert `check`, `ensure` and the watcher said current; a real `ng build` bundled B (lane C, barrier script `race-aba.sh`, `watch-aba.mjs`). **Fix** every closure file is read once into a snapshot; the hash, the esbuild loads and the TypeScript compiler host all use those bytes (`build.mjs`); the manifest therefore describes exactly what was built. **Regression** `ownership.spec.ts` "the sources change, and change back, while a build runs" (uses the test-only `createBuilder(config, { afterSnapshot })` seam; not reachable from the CLI or builders); two mutants (disk reads, hash from disk) killed.

### C4 — a stale build prunes a newer module
P2. `prune()` removed everything outside the running build's own closure. A one-off build that started before `extra.gpu.ts` existed deleted the output the dev server had just built; the server's Angular build then failed with "Could not resolve" until the next save (lane C `prune-race.mjs`). **Fix** only files listed in the manifest are removed (see L2) and the decision uses the sources as they are at prune time (`build.mjs` re-scans the closure). **Regression** `ownership.spec.ts` "a build that started with an older closure does not delete…" (mutants killed).

### C10 — stopping one dev server deletes the other's stub
P2. `watch.mjs close()` removed any stub. Two `ng serve` on one workspace with a transform error: SIGINT of the first left the second with `Could not resolve "./m1"` instead of the banner. **Fix** new `sessions.mjs`: a watcher with stubs registers `.tmp/sessions/<pid>-<n>`; `close()` removes stubs only when no other live session is registered (records of dead processes are ignored). **Verified on real `ng`** (`sm.mjs s16`, two servers on 4531/4532: first stops → stub stays, fix → replaced, last stops → removed) and by `ownership.spec.ts` (3 tests, mutant killed).

### C6 / B4 — outputs written outside the output folder
P2. A shader importing `../../shared/helpers` made `outputsOf` yield `../shared/…`; with `rootDir` = `src` TypeScript failed (TS6059) but emitted `shared/helpers.d.ts` (+ `.map`), overwriting a hand-written declaration file. **Fix** the closure is refused up front ("A shader module imports a module outside the source folder…", nothing is built) and `store()` never writes outside `out`. **Regression** `ownership.spec.ts` "modules outside the source folder" (hand-written `.d.ts` survives; mutant killed).

### C2 — concurrent prune crash
P3. Parallel builds that both pruned leftovers crashed with ENOENT on `stat` (lane C: 1 of 6 rounds of real `ng build`, 4 of 12 of the CLI). Gone with the ownership-based prune (no directory walk). **Regression** stress test "several builds that all prune the same leftovers never fail" (6 rounds × 3 builds × 12 leftovers; probabilistic before the fix, deterministic pass after).

### C5 — cache key
P3. The hash covered sources and the `typegpu`/`unplugin-typegpu` versions and the constant tool version only. **Fix** adds the tsconfig (and relative `extends`), esbuild/TypeScript/Babel versions and a digest of the tool's own code. **Regression** "a change of the tsconfig is not fresh" (mutant killed). Not tested with other esbuild/TypeScript versions installed (code and `versionsOf` output only).

### C7 — case-only rename on a case-insensitive file system
P3 (macOS/Windows). `big.gpu.ts`→`Big.gpu.ts`: the write was skipped ("same bytes") and `prune` then deleted the output under the old name. **Fix** `prune` skips a name whose lowercase twin is the same file (same inode/device). **Regression** runs only on case-insensitive file systems (APFS here); mutant killed.

### B1 — plugin mode loses Angular's default resolve conditions
**P2, independently reproduced by the Lead** (`base-plugin`, fixture package with `production`/`development`/`default` exports): `ng build` (production) bundles `default`; `ng build --conditions module --conditions production` bundles `production` (what the stock builder does). Cause: CLI fills `conditions: []` for a third-party builder; `@angular/build` treats a defined array as custom conditions; `custom-esbuild` passes it on (a stock builder with `"conditions": []` reproduces it exactly, lane B). The prebuild wrappers compensate (see the audit fix in `docs/SHADER-PREBUILD-POC.md` Follow-up 4); plugin mode cannot without changing what `ng add` writes. **Status** documented in `lib/README.md` (plugin Limits) with the verified workaround; whether `ng add` should write `conditions` is a product decision, left open. Not affected: default `ng serve` (Vite prebundle), `ng test`, the always-added `browser`/`es2020`/`import`; the default TypeGPU app's own dependencies bundled identically.

## Architecture research (read-only agents)
Two read-only studies were run on request; neither implemented anything. (1) Simpler alternatives: no supported Angular transform hook exists; routes are an external transform (generated files / a shader package), an unsupported in-Angular hook (plugin, prebuild wrappers: both use `@experimental` `@angular/build` exports; custom-esbuild `require`s the same ones), or leaving the CLI (Analog). A TS-transformer route and a runtime/no-transform route are not viable (isolatedModules bypasses `ts.emit`; typegpu needs compile-time `externals`). Conditional recommendation: stateless per-file sibling generation ("A1") if the guarantee "a bare `ng build` can never bundle a stale shader" may be dropped. (2) Hybrid: wrappers cannot be removed without weakening invariants 1-3 for bare `ng` invocations (no wrapper-free build-time hook exists: Architect has no `dependsOn`, `concat` drops flags, the CLI never runs package.json scripts); recommended H1 = keep thin wrappers + per-file sibling generation with a stateless `verify()` before and after the official builder; estimated ~40% fewer hand-written lines (an estimate, not a prototype), at the cost of a `.gpu.ts`-only convention and `./x.gpu.generated` imports. Both recommend validating with a prototype experiment (P1-P10) before rewriting anything.
